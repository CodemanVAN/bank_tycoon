# 09 — QA、测试与验收标准

## 1. 测试策略

- Domain 规则优先做单元测试；任何金融公式、政策效果和状态机转换都不能只依靠肉眼验收。
- Simulation 做集成测试和确定性回放测试。
- Godot Scene/UI 做冒烟测试和人工检查。
- Mod、存档、翻译属于输入边界，必须测试坏数据和缺失数据。

## 2. MVP 功能验收

### A. 客户完整链路

- 客户按设定的客户生成规则进入大厅。
- 客户能识别服务需求并到达正确队列。
- 有空闲员工时请求可被正确分配。
- 员工按工作时长推进请求。
- 完成请求后客户状态变化并离开或进入下一个服务。
- 无服务能力/等待超时的客户会离开并影响满意度。
- 相同 Seed 和相同命令输入可重复得到相同客户流量和业务结果。

### B. 员工系统

- 员工状态转换合法；不允许同时执行多个互斥任务。
- 调岗会清理/转移当前任务并进入适应期。
- 疲劳随工作/加班增加，休息恢复。
- 薪资和培训成本正确入账。
- 招聘/解雇/晋升会触发正确领域事件。

### C. 金融系统

- 每笔 Journal Entry 借贷平衡。
- 存款本金不计入利润。
- 贷款本金发放不计为当期收入。
- 利息按游戏日计提，速度倍率不影响金额。
- 取款同时减少现金资产和存款负债。
- 日终利润、现金、贷款、存款、权益变化可追溯。

### D. 部门与政策

- 创建部门需要满足解锁条件和资金成本。
- 部门日成本在日终结算中生效。
- 升级有明确效果差异，不能只改 UI 等级文本。
- 政策前置条件、互斥关系、资源成本都有效。
- 加载 Mod 政策/部门时，与原版内容使用同一校验规则。

### E. 事件

- 事件满足触发条件/冷却后才出现。
- 所有选项可解释，并正确修改状态。
- 事件链根据过去选项推进。
- 高严重度事件前有预警。
- 玩家选择结果进入事件历史/日终报告。

## 3. 时间与性能验收

- 暂停后模拟分钟不增加。
- 1x/2x/3x 只影响现实推进速度，不改变每个游戏日的经济结果。
- 连续运行至少 30 个游戏日无崩溃、无负余额异常、无重复结算。
- 50 个同屏动态单位时，目标机器保持 60 FPS（最终以硬件测试定义）。
- 低帧率下模拟仍按固定步长推进，不能漏结算。

## 4. 存档验收

- 自动存档成功后可读回相同核心状态。
- 中断写入不会破坏原正式存档。
- 旧版 Fixture 能迁移到当前版本。
- 缺失 Mod 时显示明确提示，不能静默删除未知内容。
- 错误 JSON/损坏存档能触发备份恢复或清晰错误提示。

## 5. Mod 验收

- 合法目录 Mod 和 ZIP Mod 可加载。
- JSON Schema 不合法时整份 Mod 拒绝注册，并输出文件/路径/错误原因。
- 重复 ID、缺依赖、循环依赖、冲突被检测。
- 路径穿越、异常尺寸图片和无效文件被拒绝。
- Mod 翻译正确回退。
- 不执行 Mod 提供的脚本或任意表达式。

## 6. 本地化验收

- 简中、英文、日文至少覆盖所有 MVP 页面和关键事件。
- 缺失 Key 在开发日志中可见。
- 切换语言后已打开 UI 正确刷新。
- 长文本不遮挡按钮或关键信息。
- 数值/货币/日期格式可按语言正确显示。

## 7. 美术验收

- Nearest/整数缩放下无模糊像素边缘。
- 同一套人物与家具的光源方向一致。
- 人物脚底锚点与地面一致，不滑步/漂浮。
- 不存在 AI 伪文字进入游戏界面。
- 重要状态不能仅靠颜色表达。
- 主大厅在 640x360 逻辑分辨率下，员工、客户和排队状态可辨认。

## 8. 发布前检查

- Godot 4.7.2 Stable 无资源导入错误、解析错误和 Missing Resource。
- 首次启动能进入主菜单/原型场景。
- 新建游戏、暂停、加速、保存/加载（已实现部分）可用。
- 语言/字体完整。
- Mod 目录为空时游戏也可正常运行。
- 所有字体、音频、图片和插件都具有明确来源/许可记录。
